# Fleet Intelligence 발표자 노트

이 노트는 [한국어 HTML 발표자료](fleet-intelligence-slides.html)의 본문 13장과 참고 5장에 대응합니다. 본문은 13장의 고객 데이터 적용 방법에서 마치고 14~18장은 질문에 답할 때 사용합니다. 기준일은 2026-09-15이며, PowerPoint에 노트를 삽입한 파일은 이번 작업에 포함하지 않습니다. **데모 지시**는 발표자 행동이며 읽지 않습니다. 원본의 짧은 무음 영상 대신 현재 앱을 직접 시연하거나 이 문서에 연결된 실제 화면을 사용합니다.

## 발표 준비

프로젝트 README에 따라 DB·모델을 준비하고 backend와 frontend를 별도 터미널에서 실행합니다. 이미 실행 중이면 다시 시작하지 않아도 됩니다. 기본 직접 모델 호출과 DB 함수 호출을 혼동하지 않도록 상단 상태와 서버 설정을 먼저 확인합니다.

```powershell
uv run --directory backend python -m app.server
npm --prefix frontend run dev
```

DB 함수 호출을 보여줄 때는 `CHAT_PROVIDER=horizondb`, `EMBEDDING_PROVIDER=horizondb`, `CAPTURE_QUERY_PLAN=true`를 설정하고 backend를 재시작합니다. 필요한 별칭은 `horizonship-chat`, `horizonship-embedding`입니다. 함수·모델·네트워크 준비가 필요하며, 화면 확인을 위해 전체 DB setup을 다시 실행하지 않습니다. 별칭 준비는 `--models-only` 절차를 따릅니다.

브라우저에서 http://127.0.0.1:5173/ 을 열고 `Clear`와 대화 초기화로 시작합니다. 상태가 `All statuses`인지 확인합니다. 화면 상태는 채팅 조건보다 우선하므로 이전 시연의 상태가 남으면 의도와 다른 결과가 나옵니다. 2026년 9월의 고정 샘플이므로 ETA 시연은 아래의 절대 날짜를 사용합니다. “이번 주” 같은 질문은 실행 날짜에 따라 결과가 달라집니다.

## 슬라이드 1 - Fleet Intelligence

Fleet Intelligence는 배송의 상태, 위치, 화물 의미를 한 화면에서 조회하는 샘플입니다. 왼쪽에서 조건을 직접 지정할 수도 있고 오른쪽에 한국어로 질문할 수도 있습니다. 두 방식은 같은 HorizonDB 데이터를 사용합니다. 제품명과 실제 화면 이름은 영어로 유지하고, 설명은 한국어로 진행하겠습니다.

데모 지시: 첫 화면의 Search Workbench, 선박 마커가 있는 지도, Shipment assistant를 차례로 가리킵니다. 상단 서비스 상태가 연결 상태를 보여주는지 확인합니다.

## 슬라이드 2 - 하나의 HorizonDB에서 업무 데이터와 AI 검색을 함께

이 샘플의 목적은 서로 다른 데이터 유형을 하나의 업무 질문에 함께 사용하는 방법을 보여주는 것입니다. 배송 상태와 ETA는 SQL 조건으로 검사하고, 위치와 권역은 PostGIS로 계산하며, 화물 설명의 의미는 벡터로 비교합니다. 원본 업무 데이터를 용도별 외부 검색 저장소로 나누지 않고 같은 HorizonDB 안의 테이블과 인덱스로 조회합니다. 하나의 데이터베이스라는 뜻이지 모든 내용을 한 테이블에 넣는다는 뜻은 아닙니다.

HorizonDB의 운영 기반과 PostgreSQL 호환성 위에서 관계형 데이터 관리와 확장 기능을 활용합니다. pgvector는 벡터 표현과 비교 연산, DiskANN은 벡터 검색 인덱스의 역할을 합니다. 업무 데이터가 바뀌면 기존 pipeline이 임베딩 갱신을 처리합니다. 각 기술을 나열하기보다 함께 조회하고 갱신하는 과정에서 어떤 역할을 하는지 설명합니다. 특정 SQL에서 항상 DiskANN을 사용한다고 소개하지 않습니다.

데모 지시: HorizonDB 내부의 정형·공간·벡터 데이터를 차례로 짚고, 데이터 변경에서 벡터 갱신으로 이어지는 흐름을 설명합니다. 외부 Foundry는 HorizonDB 경계 밖에 표시했습니다. `azure_ai`는 모델 호출 경로이며 실제 추론은 외부 서비스에서 수행됩니다. 직접 API provider도 유지되므로 모든 호출이 반드시 DB 함수를 거친다는 의미는 아닙니다.

이 시연은 24건의 고정 샘플을 사용하며 안정성·고가용성·대규모 성능을 검증하는 벤치마크는 아닙니다. 제품의 운영 특성과 이 샘플에서 확인한 동작을 구분하며, 제한사항의 상세 설명은 참고 1(14장)에 남겼습니다.

## 슬라이드 3 - 상태·시간·위치·화물 의미를 한 번에 묻는다면?

첫 질문은 지연 상태와 2026년 9월 ETA를 검사하고, 출발 좌표가 아시아 권역 안에 있는지 확인한 뒤 리튬 배터리 관련 의미를 비교합니다. 날짜와 상태를 벡터 검색어에 섞지 않고 각각의 조건을 결합합니다. 의미 검색은 품목의 정확한 일치 조건이 아니므로 결과의 화물 설명을 함께 확인합니다.

초안의 의료용품 질문은 조건을 정상적으로 조합했지만, 현재 지연·아시아 출발·9월 ETA 샘플에 해당 화물이 없어 관련성이 낮은 후보를 반환했습니다. 도입부에서는 실제 적합한 화물이 있는 리튬 배터리로 예시를 바꿨습니다. 데이터를 추가하거나 검색 로직을 바꾼 것은 아닙니다.

둘째 질문은 현재 위치가 Singapore 반경 5,000km 안에 있는 배송을 대상으로 반도체 관련 의미와 기준점까지의 거리를 함께 평가합니다. 반경 필터와 가중 정렬은 다른 처리이며, 8장에서 같은 요청의 핵심 SQL을 보여줍니다.

셋째 질문은 지연 상태·아시아 출발 조건에 맞는 배송 중 각 배송의 현재 위치에서 자기 목적지까지 거리가 짧은 순서로 2건을 찾습니다. 모든 배송이 같은 목적지를 가진다고 가정하거나 ETA 순서로 해석하지 않습니다.

2026-09-15에 앱과 같은 `/api/chat/stream` 요청 형식으로 새 질문을 확인했습니다. 화면 상태를 적용하지 않는 `status=null`로 요청했습니다.

| 질문 | 확인한 조건과 결과 |
| --- | --- |
| 리튬 배터리 복합 검색 | `cargo_query=lithium battery`, `status=delayed`, `origin_region=Asia`, ETA 2026-09-01~30. hybrid 검색 후보 3건 중 실제 리튬 배터리인 SHIP-0011이 유사도 0.5769로 첫 번째였습니다. |
| 목적지에 가까운 2건 | `status=delayed`, `origin_region=Asia`, `sort_by=destination_distance`, `result_limit=2`. SHIP-0005 약 1,066.17km, SHIP-0011 약 5,762.66km 순이었으며 추가 일치 배송이 있습니다. |

리튬 배터리 검색의 나머지 후보는 전기차와 의류로 관련성이 낮았습니다. 3건 모두 리튬 배터리라고 소개하지 않습니다. 상태·기간·권역의 정확한 조건 검사와 화물 의미의 유사도 순위를 구분해 설명합니다. 둘째 가중 검색의 실제 실행 내용은 8장 노트와 연결합니다.

데모 지시: 세 질문 아래의 데이터 조합을 비교합니다. 모든 질의가 모든 데이터 유형을 반드시 사용하는 것은 아닙니다. 업무 질문에 필요한 정형·공간·벡터 조건을 같은 조회에서 조합할 수 있다는 점이 중심 메시지입니다. 이어지는 4장에서 직접 조건 입력과 자연어 질문이 같은 Repository를 사용하는 구조로 연결합니다.

택시나 버스 배차에도 비슷한 질문이 생길 수 있지만, 이 앱에 배차 기능이 구현돼 있다는 뜻은 아닙니다. 이번 시연은 배송 조회만 다룹니다.

## 슬라이드 4 - 두 진입점과 공용 Repository

Search Workbench는 `/api/search/criteria`로 명시적 조건을 보냅니다. 조건 해석이나 답변 작성에 LLM을 사용하지 않으며 화물 검색어가 있을 때만 임베딩을 생성합니다. 채팅은 `/api/chat/stream`으로 현재 질문을 보내고 Agent Framework가 구조화된 검색 도구를 호출합니다. 기존 `/api/search`는 별도의 벡터 검색 API로 유지됩니다.

원본과 달리 채팅에는 화면의 상태 선택이 적용됩니다. ETA, 지도 반경, 왼쪽 화물 검색어는 전달하지 않습니다. 이전 대화 전체도 서버로 전송하지 않으므로 후속 질문에는 필요한 조건을 다시 포함해야 합니다.

## 슬라이드 5 - 두 가지 입력 방식, 같은 배송 데이터

앞 장의 구조가 실제 화면에서는 이렇게 보입니다. 왼쪽에서는 알고 있는 조건을 직접 지정하고, 오른쪽에서는 자연어로 질문합니다. 두 방식 모두 같은 HorizonDB의 배송 데이터를 조회하며, 가운데 지도에서 결과의 현재 위치를 확인합니다. 입력 방식은 달라도 별도의 데이터 사본을 검색하는 것은 아닙니다.

데모 지시: 왼쪽 Search Workbench, 가운데 지도, 오른쪽 Agent with Tools 순으로 가리킵니다. 컨트롤을 하나씩 설명하지 않고 다음 장에서 검색에 필요한 컬럼을 짚은 뒤 세 가지 복합 질의로 이어갑니다. 전체 테이블 구조는 참고 3(16장), 직접 조건 입력 방법은 참고 4(17장)에서 질문에 답할 때만 엽니다.

선택적 지도 시연: 배송 카드 하나를 선택하고 상세의 배송 번호와 지도 마커를 비교합니다. 채팅 결과가 있으면 `현재 위치 보기`로 이동합니다. 이전 팝업이 남지 않는지 확인합니다.

선박 아이콘의 색은 상태를 나타냅니다. 출발지 기준 검색에서도 지도는 현재 위치를 보여줍니다. 경로는 출발지·현재 위치·도착지를 잇는 개략 선이며 실제 항적이나 해상 항로가 아닙니다. 날짜 변경선을 넘을 때는 화면 전체를 가로지르는 선이 생기지 않도록 분리했습니다.

## 슬라이드 6 - 복합 검색에 사용하는 데이터

이 장은 전체 스키마 설명이 아니라 다음 세 질의의 SQL을 읽기 위한 안내입니다. `shipments`의 `status`와 `eta`는 정형 조건이고, `origin_position`, `destination_position`, `current_position`은 각각 SRID 4326 Point입니다. 실제 이름·metadata 등 다른 컬럼은 참고 3에서 설명합니다.

벡터는 배송 행 안에 있지 않습니다. `shipment_embeddings.shipment_id`가 `shipments.id`를 참조하며, `embedding`은 vector(1536)입니다. 의미 검색에서는 두 테이블을 JOIN하고 검색어 벡터와 `<=>`로 비교합니다. `region_boundaries`와는 FK로 연결하지 않고 `ST_Covers`로 좌표와 경계를 비교합니다.

반경·거리 계산은 geometry를 geography로 변환해 m 단위로 수행합니다. 목적지까지 거리는 결과에서 1000으로 나누어 km로 표시합니다. 임베딩 갱신용 job과 버전은 12장에서 설명하므로 여기서는 컬럼을 나열하지 않습니다.

## 슬라이드 7 - 상태·기간·출발 권역·화물 의미로 찾기

데모 지시: 상태를 All statuses로 두고 슬라이드의 리튬 배터리 질문을 실행합니다. 조건이 `status=delayed`, ETA 2026-09-01~30, `origin_region=Asia`, `cargo_query=lithium battery`인지 확인합니다. 모델 해석이 다르면 실제 값을 먼저 설명합니다.

상태·ETA는 정확한 조건으로 검사하고, 출발 좌표는 `ST_Covers`로 Asia 경계와 비교합니다. 날짜와 권역을 벡터 검색어에 섞지 않습니다. `lithium battery`만 임베딩하며 벡터 거리 오름차순으로 정렬합니다. 유사도 표시는 1 - cosine distance입니다. ETA는 저장된 도착 예정일이지 도착 이력이 아닙니다.

2026-09-15 실제 `/api/chat/stream` 검증에서 후보 3건 중 SHIP-0011이 첫 번째였으며 유사도는 0.5769였습니다. 나머지는 전기차와 의류로 관련성이 낮았습니다. 세 건 모두 리튬 배터리라는 뜻이 아닙니다. 이 문서 개정에서는 모델을 다시 호출하지 않고 이전 검증 기록을 사용했습니다.

7~9장의 코드는 Repository의 조건·계산·정렬을 발췌해 줄바꿈한 것입니다. 단독 실행 SQL이 아닙니다. 전체 SELECT, JOIN, 상태 null 검사, 벡터 content version 검사, 공통 LIMIT 등의 일부는 생략했습니다. 특히 9장의 `ST_Covers`는 실제 SQL에서 Asia 이름 조건과 함께 EXISTS 안에 있습니다. 전체 SQL과 순서별 바인딩 값은 해당 요청의 실행 내역에서 확인합니다.

권역은 Natural Earth의 단순화된 육지 경계라 해안 밖 항만이 제외될 수 있으며 도시 이름으로 보완하지 않습니다. 7~9장은 하나의 결과를 이어서 거르는 단계가 아니라 독립적인 업무 질문입니다.

## 슬라이드 8 - 반경 안에서 의미와 거리로 정렬하기

데모 지시: 상태를 All statuses로 두고 슬라이드의 반도체·Singapore 질문을 실행합니다. `sort_by=semantic_spatial`, `position_field=current`, `cargo_query=semiconductor`, `nearby_location=Singapore`, `radius_km=5000`을 확인합니다.

2026-09-15 실제 실행에서 6건을 반환했습니다. 반도체 웨이퍼가 있는 샘플로 의미 검색을 설명하되 다른 화물도 후보에 포함될 수 있음을 안내합니다. [같은 요청의 실제 SQL 캡처](media/fleet-weighted-sql.png)를 보존했습니다. 본문은 세 질의의 형식을 맞추기 위해 캡처 대신 핵심 SQL 발췌를 사용합니다. 다른 요청의 화면을 이 요청의 결과처럼 소개하지 않습니다.

Singapore 기준점은 경도 103.8198, 위도 1.3521입니다. `ST_DWithin`에 반경 5000000m를 바인딩하고, 가중 점수에는 반경 5000km를 사용합니다. 상태 바인딩 두 값은 null이며 검색어 벡터는 1,536차원입니다. 점수 계산식은 다음과 같습니다. 본문 왼쪽에는 의미와 거리의 계산식을 표시하고, 오른쪽 SQL에는 `hybrid_score`로 정렬하는 부분을 표시했습니다. 왼쪽 계산식은 설명용 표기이며 실행 SQL이 아닙니다.

```text
hybrid_score = (
  0.72 * cosine_similarity
  + 0.28 * max(0, 1 - distance_to_center_km / radius_km)
)
```

가중 점수는 성공 확률이 아닙니다. 기본 반경 검색은 자동으로 가중 정렬하지 않습니다. 전체 적격 레코드를 평가한 뒤 LIMIT을 적용하므로 데이터가 커지면 비용을 별도로 검토합니다. 채팅의 5,000km 예시는 Workbench 반경 슬라이더 상한 3,000km와 다릅니다.

## 슬라이드 9 - 조건에 맞는 배송을 목적지 거리순으로 찾기

데모 지시: All statuses에서 “아시아에서 출발한 지연 배송 중, 목적지에 가장 가까운 2건을 찾아주세요”를 실행합니다. `status=delayed`, `origin_region=Asia`, `sort_by=destination_distance`, `result_limit=2`를 확인합니다.

2026-09-15 실제 검증에서는 SHIP-0005 약 1,066.17km, SHIP-0011 약 5,762.66km 순이었으며 `has_more=true`였습니다. 거리는 각 배송의 현재 위치에서 자기 목적지까지 계산합니다. 같은 도시를 기준으로 정렬하거나 ETA 순으로 정렬하는 것이 아닙니다. 실제 해상 항로 거리도 아닙니다.

SQL은 추가 결과 유무를 확인하려고 표시 건수보다 한 건 더 요청할 수 있습니다. 따라서 상위 2건을 표시한다고 LIMIT 바인딩 값이 반드시 2인 것은 아닙니다. 이 요청에는 의미 조건이 없어 검색어 임베딩을 하지 않지만, Agent의 조건 해석·답변 생성에는 채팅 모델을 호출합니다.

목적지 거리순에서 상태를 지정하지 않으면 delivered를 제외합니다. 여기서는 delayed를 명시했습니다. 화물 의미와 목적지 거리 정렬의 조합은 현재 지원하지 않습니다. SHIP-0024의 `unknown`은 위치 갱신 미보고를 가정한 명시적 샘플 상태이지 렌더링 실패의 기본값이 아닙니다.

## 슬라이드 10 - 등록한 모델을 DB 함수에서 호출하기

이 장은 호출 위치와 모델 역할을 설명합니다. DB 경유 검색은 `CHAT_PROVIDER=horizondb`, `EMBEDDING_PROVIDER=horizondb`를 기준으로 합니다. `model_registry.model_add`는 외부 endpoint, deployment, 인증 정보를 별칭으로 등록하며 DB 안에 모델 가중치를 설치하지 않습니다. 슬라이드의 등록 표기는 개념용이며 실행 가능한 등록 SQL이나 인증 값을 표시한 것이 아닙니다.

`horizonship-chat`은 GPT-5.4 deployment, `horizonship-embedding`은 text-embedding-3-small deployment를 가리킵니다. `azure_ai.generate(prompt, alias, system_prompt)`는 조건 해석과 답변 생성에, `azure_openai.create_embeddings(alias, text)`는 검색어 임베딩에 사용합니다. pipeline의 `ai.embed`는 검색어가 아니라 변경된 배송 텍스트를 처리하며 상세는 12장에서 이어갑니다.

실제 추론은 외부 Foundry에서 실행됩니다. 기본 OpenAI SDK 직접 호출 경로도 유지하고 있으며, 어느 provider를 선택하든 배송 변경 pipeline은 DB에서 실행됩니다. 등록 함수·인증 방식은 설치된 확장 버전의 제약을 따릅니다. 현재 azure_ai 2.2.2의 등록에는 subscription key를 사용할 수 있는 외부 endpoint가 필요합니다. 새 Entra ID 전용 Foundry가 곧 모든 DB 호출 경로를 지원한다고 설명하지 않습니다.

## 슬라이드 11 - 질문에서 검색 결과와 답변까지

8장의 반도체·Singapore 반경 질문을 다시 사용하되 검색 사례를 반복 시연하지 않고 처리 과정을 짚습니다. DB provider는 첫 모델 호출에서 search 또는 clarify와 조건 JSON을 받습니다. 슬라이드 JSON은 그중 주요 검색 인자만 발췌한 것이며 전체 모델 응답 형식은 아닙니다.

Python이 JSON과 ShipmentFilters를 검사하고 Agent Framework가 `search_shipments` 도구를 요청당 최대 한 번 호출합니다. 화면의 상태 조건이 우선 적용됩니다. Repository가 semiconductor를 벡터로 변환하고, 8장의 반경 검사와 가중 정렬 SQL을 구성해 실행합니다. 그 결과를 두 번째 모델 호출에 전달하여 한국어 답변을 작성합니다. 카드와 지도에는 도구가 반환한 배송 레코드를 사용합니다.

모델은 임의 SQL을 작성해 실행하지 않습니다. 모호하거나 지원하지 않는 조건에는 검색 없이 확인 질문을 합니다. 검색 오류를 0건으로 바꾸지 않습니다. Python 도구는 애플리케이션에서 실행되며 `azure_ai.generate`를 사용한다고 Agent Framework가 DB 안으로 이동하는 것은 아닙니다. DB 모델 호출이 길어지면 풀 연결 점유와 외부 호출 비용에도 영향을 줄 수 있습니다.

## 슬라이드 12 - 배송 변경에 따라 임베딩 갱신하기

이 장부터는 검색 시 처리가 아니라 데이터 변경 시 처리입니다. 초기 setup은 backfill로 벡터를 채운 뒤 인덱스와 pipeline, 배송 변경 trigger를 준비합니다. 이후에는 애플리케이션의 검색 요청과 별개로 DB pipeline이 벡터를 갱신합니다.

첫 번째 변경 감지는 shipments의 trigger입니다. INSERT 또는 title, description, origin_name, destination_name, current_location_name, status, metadata의 UPDATE를 대상으로 실제 값이 달라졌는지 비교합니다. 임베딩 입력에는 이 필드들이 포함됩니다. 좌표, ETA, updated_at만 바뀌면 새 임베딩을 요청하지 않습니다. 예를 들어 description의 화물 설명을 바꾸면 job을 갱신하지만 ETA만 바꾸면 갱신하지 않습니다.

trigger는 배송별 job 한 행을 upsert합니다. embedding_input은 필드를 합친 텍스트이고 content_version은 변경마다 증가합니다. 이는 이벤트마다 행을 추가하는 영구 이력 테이블이 아닙니다. 두 번째 변경 감지는 job을 source로 삼는 pipeline의 on_change입니다. `ai.table_source(shipment_embedding_jobs)` → `ai.embed(embedding_input, horizonship-embedding, 1536)` → `ai.table_sink(shipment_embeddings)` 순서이며 shipment_id 충돌 시 벡터와 버전을 upsert합니다.

데모 지시: 오른쪽 SQL에서 `SELECT ai.create_pipeline(...)`과 `trigger => 'on_change'`를 가리킵니다. 이 선언은 [초기화 코드의 CREATE_PIPELINE_SQL](../backend/app/setup_database.py#L135)을 줄바꿈만 줄여 표시한 것입니다. `source`는 shipments가 아니라 job 테이블이며 `incremental_column`은 `updated_at`입니다. `steps`에서 embedding_input을 모델에 전달하고 `sink`에서 shipment_id 충돌을 처리합니다. 앞의 배송 trigger는 변경 대상을 선별하고, 이 설정은 job의 변경에 따라 pipeline을 실행합니다.

`%s` 세 곳에는 pipeline 이름, 임베딩 모델 별칭, 충돌 시 UPDATE 절을 순서대로 바인딩합니다. 마지막 값은 [PIPELINE_SINK_ACTION](../backend/app/setup_database.py#L128)으로, embedding_input·content_version·updated_at·metadata·embedding을 새 값으로 갱신합니다. 화면의 SQL은 실제 파라미터화된 선언이므로 값을 바인딩하지 않고 SQL 편집기에 그대로 실행하는 예제가 아닙니다. 시연 중 pipeline을 다시 생성하지 않고 선언만 짧게 설명합니다.

현재 pipeline에는 청킹 단계가 없습니다. 배송별 텍스트를 벡터 하나로 만듭니다. 긴 문서를 여러 청크로 나누는 구성을 추가하려면 청크 식별자와 sink 구조부터 별도로 설계해야 하므로 현재 구현처럼 설명하지 않습니다.

검색 시 job이 없거나 job과 sink의 content_version이 같아야 해당 벡터를 사용합니다. 버전이 다르면 갱신 대기 중인 이전 벡터를 의미 검색에서 제외합니다. 정형·공간 조건만 사용하는 조회까지 막는 것은 아닙니다. 시연을 위해 스키마나 인덱스, 샘플을 다시 만들지 않습니다.

## 슬라이드 13 - 고객 데이터로 적용하는 방법

12장에서 이 장으로 넘어가며 설명합니다. “지금까지는 배송 데이터를 예로 들었습니다. 고객 업무에 적용할 때는 먼저 어떤 질문에 답해야 하는지 정하고, 그 질문에 필요한 정형 필드·위치·설명 데이터를 연결합니다. 데이터가 바뀔 때 어떤 내용의 임베딩을 갱신할지도 정합니다. 이 샘플을 출발점으로 고객 데이터의 검색 결과를 확인할 수 있습니다.”

표는 기능 목록을 다시 읽기 위한 것이 아니라 고객이 바꿀 부분을 정리한 것입니다. 검색 대상과 필수 조건, 결과에 보여줄 항목부터 정합니다. 다음으로 좌표·권역의 기준과 의미 검색에 넣을 설명 필드, 정렬 방식을 선택합니다. 마지막으로 재임베딩이 필요한 변경과 갱신 주기·처리 방식을 검토합니다. 모든 고객 질문에 공간·벡터 검색을 반드시 넣는다는 뜻은 아닙니다.

현재 샘플은 정해진 필터와 on_change pipeline을 사용합니다. 표의 고객 업무 항목은 수정·검토할 내용이며, 임의 컬럼이나 갱신 주기를 화면 설정만으로 바꿀 수 있다는 뜻이 아닙니다. 필요한 경우 스키마, 입력 규격, Repository의 SQL, 임베딩 입력과 pipeline을 수정합니다. 모델·차원·입력 필드를 바꾸면 기존 벡터 재생성과 검색 결과도 확인해야 합니다.

데모 지시: 고객의 대표 질문과 사용할 수 있는 샘플 데이터를 확인합니다. 각 질문에 기대하는 결과와 반드시 지켜야 할 조건을 정하고, 실제 조회 결과와 비교하는 것으로 첫 적용 검토를 시작합니다. 인증·권한·마스킹·운영 성능은 별도 검토가 필요하지만 마지막 장의 중심은 고객의 첫 적용 방법입니다.

본문 발표는 이 장에서 마칩니다. 이후에는 14~18장의 검증·운영, 예상 계획, 전체 테이블, 직접 조건 입력, 실행·배포 참고 자료를 필요한 질문에만 사용합니다. 구현 상세는 [기술 설명](blog-post.html), 설정과 API는 [프로젝트 README](../README.md), 출처는 [문서 출처와 라이선스](THIRD-PARTY-NOTICES.md)에서 확인합니다.

## 슬라이드 14 - 검증 범위와 운영 적용 전 확인

## 슬라이드 15 - 예상 계획과 측정 시간을 구분

필요하면 원본·정돈 보기, 줄바꿈, 복사, 6:4 분할선과 두 번 클릭 복원을 시연합니다. 계획 노드와 SQL 범위 연결은 추정이며 모호하면 강조하지 않습니다. 조작법을 본문 설명의 중심으로 삼지 않습니다.

## 슬라이드 16 - HorizonDB에 저장하는 데이터

참고 3입니다. 검색 컬럼만 다룬 6장과 달리 job과 임베딩 갱신 관계를 포함해 전체 테이블의 역할을 설명할 때 사용합니다.

배송의 상태와 위치는 `shipments`에, 1,536차원 벡터는 `shipment_embeddings`에 저장합니다. 두 테이블은 배송 ID로 연결됩니다. 의미 필드가 바뀌면 작업 테이블과 `on_change` pipeline이 벡터 갱신을 처리합니다. 권역 경계는 별도 `region_boundaries` 테이블에 있습니다. 원본처럼 배송 한 행에 벡터를 넣는 구조로 바꾸지 않았습니다.

B-tree, GiST, DiskANN이 있어도 모든 요청에서 특정 인덱스를 사용한다고 단정하지 않습니다. 실제 접근 경로는 조건과 통계에 따라 달라집니다.

현재 DiskANN 설정은 `spherical_quantized=true`, `sq_bits=4`, `sq_training_samples=25000`입니다. 25,000은 training sample 설정값이지 적재한 배송 건수가 아닙니다. 새 풀 연결마다 DiskANN SESSION 설정 6개를 한 번 적용하며 요청마다 반복하지 않습니다. job의 nullable embedding 컬럼은 azure_ai 2.2.2 호환용 placeholder이고 실제 검색 벡터는 sink에 저장합니다.

## 슬라이드 17 - Search Workbench에서 직접 지정하는 조건

참고 4입니다. 직접 조건 검색을 시연하거나 사용자가 입력 방법을 물을 때 사용합니다.

데모 지시: `Search intent`를 비워 두고 Status를 Delayed로 선택합니다. ETA를 `2026-09-15`, 허용 일수를 `15`로 설정하고 검색합니다. 적용 범위가 `2026-08-31`부터 `2026-09-30`까지임을 확인합니다. 확인 후 `Clear`를 누릅니다.

## 슬라이드 18 - 현재 저장소의 실행과 배포 범위

## 녹화와 화면 캡처

HTML 발표자료와 앱 창을 나란히 준비하고 슬라이드 단위로 녹화를 나누면 모델 대기와 준비 시간을 편집하기 쉽습니다. 대기 시간을 편집했다면 실제 처리 시간으로 오해하지 않도록 표시합니다. 고정 영상이 없거나 모델 호출이 실패하면 발표자료의 캡처를 과거의 실제 실행 화면으로 소개합니다. 실패한 현재 요청을 성공한 것처럼 설명하지 않습니다.

발표자료는 레퍼런스와 같은 16:9 고정 구성입니다. 화면에 맞춰 전체 장면을 축소하며 방향키·Page Up/Down·Home/End와 화면 버튼으로 이동합니다. 모바일에서는 가로 보기를 권장합니다. 캡처를 누르면 원본 이미지가 열리고, 브라우저 인쇄에서는 전체 18장을 장별로 출력합니다. 캡처는 2026-09-15 현재 앱 기준이며 원본 저장소의 문서와 이미지는 [출처 고지의 고정 커밋 링크](THIRD-PARTY-NOTICES.md)에서 확인합니다.
